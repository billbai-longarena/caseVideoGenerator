# 案例视频生产系统持续优化工作流

## 适用范围

用于把生产、调试和验收中的发现沉淀到 Skill、工作流、知识库、数据合同、校验器或共享引擎。目标是让系统持续进化，同时避免把单案例风格、临时参数和未经验证的偏好写死在 Skill 中。

## 1. 记录证据

- 写清触发案例、观察到的问题、影响范围、复现方式和当前临时处理。
- 区分事实、判断和审美偏好。
- 判断问题是一次性素材/编排问题，还是已经跨案例出现的系统问题。
- 记录问题最早可以在哪个低成本阶段被发现，以及它实际上在哪个阶段才暴露。若机器可判定的问题直到付费生图、长片渲染或人工交付检查才出现，把它标记为“缺失阶段门禁”，而不只标记为案例失误。

质量门：能说明“什么条件下出现什么问题”，而不是只有抽象结论。

## 2. 选择归属层

| 发现类型 | 优先归属 |
| --- | --- |
| 本案例节奏、素材、角色、措辞或例外 | `output/<project>/` |
| 可迁移的叙事、视觉、TTS 或 QA 方法 | `docs/knowledge-base/` |
| 阶段顺序、输入输出或人工质量门 | `workflows/` |
| 可确定判断的字段、引用、边界或时序规则 | schema / builder / validator / tests |
| 跨案例渲染能力或运行时缺陷 | 共享 Remotion / 脚本引擎 |
| 任务识别、工作流选择或跨阶段安全底线 | Skill |

制度、经验范围、审美倾向和单个样片的镜头节奏不自动升级为 Skill 规则。只有稳定影响任务路由、工具选择或跨阶段安全的结论才进入 Skill。

质量门：改动落在能承担该责任的最低层，没有在多个层重复维护同一组细节。

## 3. 设计最小改动

- 先定义预期行为、兼容范围和验收条件。
- 机器可判定的问题优先进入校验器并补失败测试；不要只写文档提醒。
- 需要创作判断的问题保留为方法、问题清单或软提示；不要升级为全局硬错误。
- 共享引擎新增能力时保留旧数据的回退路径，案例专属数据继续由 JSON 驱动。
- Skill 改动保持短小，链接到负责细节的 workflow、知识库或 contract。
- 对重复出现且机器可判定的问题，必须形成一条闭环：失败样例或夹具 → 失败测试 → 最早低成本阶段的门禁 → 人类可读报告 → 至少一个既有项目回归。只增加文档提醒不能关闭这类问题。
- 门禁按成本分层：plan readiness 只依赖 timeline、storyboard、prompt 和 provenance 声明，阻止错误进入付费生图；render readiness 使用真实素材、严格 validator 和短证明渲染，阻止错误进入完整长片渲染。不要把所有检查堆到交付末端。

质量门：能明确哪些行为被改变、哪些自由度被保留、旧案例怎样继续工作。

## 4. 实施并做回归

按改动层级选择验证：

- 文档/工作流：检查链接、职责边界和重复规则。
- Skill：运行 skill quick validation，并确认 description、路由和引用可用。
- builder/validator：运行成功、失败和旧项目兼容测试。
- Remotion/脚本：运行 typecheck、示例渲染和相关项目检查。
- 影响成片：运行 ffprobe、黑帧检测、关键帧或 contact sheet 视觉 QA。
- 阶段门禁：用现有素材先跑 `scripts/case-video ready output/<project> --stage plan` 和 `--stage render`，记录 blocker、warning、耗时与误报；只有阻断条件稳定且可解释时才自动接入昂贵命令。

质量门：新场景通过，至少一个旧案例保持通过；没有用新硬规则误伤合理创作差异。

## 5. 复盘矩阵

每次系统性事故至少回答以下五项，并把结论放入对应责任层：

| 问题 | 必须回答 |
| --- | --- |
| 发生机制 | 哪个数据、调度器、素材或共享状态产生了错误？ |
| 漏检机制 | 为什么已有 validator、评估器或人工步骤没有提前阻断？ |
| 最早检查点 | 在不调用 TTS、生图或长渲染的前提下，最早能验证什么？ |
| 证明方式 | 用哪个最小真实样本、短证明渲染或像素指标确认修复？ |
| 防回归 | 哪个测试、门禁、输入哈希和报告确保相同条件再次出现时失败？ |

## 6. 决定是否推广

- 单次发现先保留在案例复盘或知识库候选项。
- 跨案例复现、已有明确收益并通过回归后，再提升到 workflow、validator、engine 或 Skill。
- 如果新规则产生大量合理例外，降级为软提示、方法建议或案例参数。
- 记录回滚条件：出现哪些兼容性、质量或维护成本问题时撤回推广。

质量门：推广依据可追溯，规则强度与证据强度匹配。
